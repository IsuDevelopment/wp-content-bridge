## Public plugin surface

Five private, read-only Abilities exist:

- `wp-content-bridge/search-content`
- `wp-content-bridge/get-content`
- `wp-content-bridge/get-url-seo`
- `wp-content-bridge/get-editorial-context`
- `wp-content-bridge/get-diagnostics`

All require `wpcb_read_content`. Object reads additionally enforce the
per-post-type READ policy and native WordPress object access. No write Ability
exists yet. The settings matrix is stored in `wpcb_content_type_access`; future
writes depend on READ by domain rule.

**Write foundation (M5 Plan 1) — installed, dormant.** `src/Domain/Mutation/`,
`src/Application/Mutation/`, and two new `src/Infrastructure/WordPress/` classes
provide the write scaffolding, but **no write ability is registered**. On
activation the `Installer` (schema v4) grants `wpcb_edit_content`,
`wpcb_manage_seo`, `wpcb_publish_content` to `administrator`, registers the
options `wpcb_writes_enabled` and `wpcb_publish_enabled` (both `false`,
non-autoloaded), and creates the capped audit table
`{prefix}wpcb_audit`. `WordPressAuditLog` writes redacted rows (field names
only) and fires `do_action( 'wpcb_mutation', $event )`. Because abilities are
registered only when their master flag is on, the write surface is invisible
over MCP until an administrator enables it.

Content search applies authorization before pagination, caps candidate scans at
1,000, and labels inexact totals. Detail representations have a combined 2 MiB
limit. Content and SEO stay separate/composable per ADR 0008.

`get-editorial-context` is a bounded context-only composition Ability. It
supports `post_types`, `taxonomies`, `terms`, `authors`, `recent_content`, and
`local_businesses`. Effective types require both READ and SEARCH policy. Recent
content is published and filtered through the existing per-object authorization
path before pagination. Authors are only those observed in readable results and
expose only ID/display name. Local data comes only through the normalized SEO
provider; the Ability never reads Local options and never calls an LLM or
generates a plan.

## SEO implementation state

Normalization schema is `1.1`.

The provider-neutral model lives in `src/Domain/Seo`; orchestration and ports in
`src/Application/Seo`; Yoast adapters in `src/Infrastructure/Yoast`.

`YoastSeoProvider` now provides:

- documented `YoastSEO()->meta->for_post()` / `for_url()` resolved output;
- title, description, canonical, robots, Open Graph, Twitter, bounded Schema;
- a narrow, version-gated Yoast 28.x configured-meta allowlist;
- safe `premium`/`local` detection and `module_versions` only;
- Premium 28.x primary/additional phrases through
  `PremiumKeyphraseNormalizer`;
- detailed `{keyphrase, role, score}` values while retaining the simple phrase
  list;
- public Local Place/LocalBusiness profiles through `LocalSchemaProjector`;
- explicit/inherited/generated/unavailable/unsupported states, provenance,
  completeness, and bounded warnings.

`LocalSchemaProjector` reads only provider-emitted public Schema. It recursively
allowlists scalar business fields, PostalAddress, GeoCoordinates, opening hours,
image/logo references, `parentOrganization`, `branchOf`, and `mainEntityOfPage`;
it resolves public `@id` references and caps entities/lists. It never dumps Local
options.

For `local_businesses`, `YoastSeoProvider` sources the graph from
`WordPressRenderedSchemaReader` (a bounded, same-origin, cached loopback fetch of
the target's public JSON-LD) when the `local` module is active, because Yoast
Local's branch schema (`parentOrganization`) exists only in the front-end render.
It falls back to the resolved meta surface with a warning when the fetch fails
(source `yoast.schema.local.rendered` vs `yoast.schema.local`). See ADR 0009.

No arbitrary post meta, raw provider options, license/update state, secrets, or
Yoast indexables-table rows are returned.

## Important limitations

- Premium synonyms are not implemented: their stable 28.x contract was not
  proven, so do not guess the storage format.
- Yoast's documented analysis-score Abilities return recent-post lists without
  stable post IDs. Do not attach those scores to a requested target.
- Local multiple-location branch schema (`parentOrganization`, branch address,
  geo, hours) is emitted only on a front-end render; the resolved meta surface
  and REST `yoast_head_json` omit it. The provider captures it via a bounded
  same-origin rendered-schema fetch (ADR 0009), verified at runtime. On a
  self-signed local host the loopback needs `sslverify` disabled — set the
  `wpcb_seo_rendered_schema_sslverify` filter to `__return_false` (the runtime
  script installs a temporary mu-plugin that does this and removes it on exit).
- Homepage/archive indexables may be unavailable locally; return the explicit
  unavailable state rather than failing content reads.
- CLI `WP_HOME` is malformed in this Local config because it depends on
  `HTTP_HOST`; URL-selector tests must use the real HTTPS route.
- WP-CLI 2.11 prints PHP 8.4 deprecations from its bundled Runner/Mustache code;
  they are not plugin warnings.
